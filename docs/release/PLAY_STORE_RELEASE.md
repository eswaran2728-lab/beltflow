# Releasing BeltFlow on Google Play

Prepared 2026-11-17. This guide takes BeltFlow from this repository to a
Google Play release. Steps marked **Owner** need your Google account, your
payment details or your decision; everything else is already in the
repository.

Play Console and Render change their screens often. If a menu name below
differs, look for the nearest match. Nothing in this guide uploads or
publishes anything automatically.

## Decisions already made

| Decision | Choice | Why |
|---|---|---|
| App ID | `com.eswaran.beltflow` | Most likely the listing already in your Play Console (the older app reached version code 16). Keeping it keeps one listing. An app ID can never change after publishing. If this ID is **not** in your Play Console, it is still fine as a new app |
| Testing APK ID | `com.eswaran.beltflow.testing` | Testers can install it next to the store app; it can never replace it |
| Version codes | 100 + build number | Always higher than the old app's 16 |
| Hosting | Render, Singapore region | Closest region to Malaysia; deploys from GitHub; managed PostgreSQL; secrets generated by Render, never in git. Check prices on render.com before creating it |
| Server package | `Dockerfile` + `render.yaml` | The same image runs on any host if you move later |

## Order of work

1. Replace the leaked signing key (Owner)
2. Put the server online (Owner, about 20 minutes)
3. Finish the legal pages (Owner)
4. Merge the work into `main`
5. Build the bundle on GitHub
6. Set up Play Console and upload to internal testing (Owner)
7. Closed testing, then production (Owner)

## 1. Replace the leaked signing key (Owner)

The old release keystore and its password are public in the git history.
Treat them as known to anyone.

1. On your own computer (not on GitHub), create a new upload key. Java's
   `keytool` comes with Android Studio or any JDK:
   ```bash
   keytool -genkeypair -v -keystore beltflow-upload.jks -alias beltflow-upload -keyalg RSA -keysize 2048 -validity 10000
   ```
   Choose a long password and store it in a password manager. Keep the
   `.jks` file backed up somewhere safe and **never commit it**.
2. Export its certificate:
   ```bash
   keytool -export -rfc -keystore beltflow-upload.jks -alias beltflow-upload -file beltflow-upload-certificate.pem
   ```
3. **If the app already exists in Play Console:** Play Console > your app >
   Test and release > App integrity > App signing > "Request upload key
   reset". Give the reason (key compromised) and upload the `.pem` file.
   Google normally takes a few days to approve.
   **If it is a new app:** you will choose "Let Google manage and protect
   your app signing key" when you create the first release; the upload key
   is then simply the key you sign with.
4. Add four repository secrets on GitHub: repository > Settings > Secrets and
   variables > Actions > New repository secret:
   - `PLAY_UPLOAD_KEYSTORE_BASE64`: the keystore as one line of base64
     (`base64 -w0 beltflow-upload.jks` on Linux, `certutil -encode` on
     Windows then remove the header lines)
   - `PLAY_UPLOAD_KEYSTORE_PASSWORD`
   - `PLAY_UPLOAD_KEY_ALIAS` (`beltflow-upload`)
   - `PLAY_UPLOAD_KEY_PASSWORD`
5. Delete the old secrets `RELEASE_KEYSTORE_BASE64`, `KEYSTORE_PASSWORD`,
   `KEY_ALIAS` and `KEY_PASSWORD` if they exist.

## 2. Put the server online (Owner)

1. Create an account at render.com and connect your GitHub account.
2. New > Blueprint > choose the `beltflow` repository. Render reads
   `render.yaml` and shows a database and a web service, both in Singapore.
   If Render rejects a field (for example a plan name), pick the nearest
   option it offers.
3. When asked for `CORS_ALLOWED_ORIGINS`, enter the address of your web app,
   for example `https://beltflow-api.onrender.com` (the service's own address
   works if the web app is served from the same server). Exact `https://`
   addresses only, comma separated.
4. Apply. Render generates every secret. The server checks its own
   configuration and refuses to start if anything is missing.
5. When the deploy shows "Live", open `https://<your-service>.onrender.com/api/health/ready`.
   It should say `"status":"ready"`.
6. Create the first Super Admin straight away:
   - In Render, open the service > Environment > copy `BELTFLOW_SETUP_TOKEN`.
   - Open `https://<your-service>.onrender.com/`, choose "Initialize First
     Super Admin", paste the code into "Setup code", and finish the form.
   - Without the code nobody can claim the platform, but do this before
     sharing the address anyway.
7. In GitHub: Settings > Secrets and variables > Actions > Variables > New
   variable `BELTFLOW_API_URL` = `https://<your-service>.onrender.com`.

Uploaded training videos are stored on the service's disk
(`/var/data/media`). Render's disk is attached to one instance; back it up
before you scale up. The database has its own backups in Render.

## 3. Finish the legal pages (Owner)

1. Edit `legal/business.js`: registered business name, SSM number, address,
   e-mail, phone, personal-data contact, hosting location (`Singapore` if you
   use the Blueprint), then set `complete: true`. The "Draft" notices
   disappear.
2. Have a Malaysian lawyer read the five pages in `/legal`
   (see `docs/claude-handover/14_PRIVACY_LEGAL_ACCESSIBILITY_2026-11-15.md`
   for the points to confirm).
3. Your public addresses become:
   - Privacy policy: `https://<your-service>.onrender.com/legal/privacy.html`
   - Account deletion: `https://<your-service>.onrender.com/legal/delete-account.html`

## 4. Merge into `main`

Render deploys from `main`, so the server code and legal pages must be
merged first. Ask Claude to merge, or merge the pull request yourself.

## 5. Build the bundle on GitHub

GitHub > Actions > "Build BeltFlow Play Store bundle (AAB)" > Run workflow >
branch `main` (leave the address empty to use `BELTFLOW_API_URL`).

The run checks that the address is `https://`, that plain-HTTP traffic is
off, and that the app ID is right, then builds and signs the bundle. When it
finishes, download the artifact `beltflow-play-bundle-<number>`.

The log step "Show the signing certificate" prints the certificate's SHA-256.
It must match the upload certificate in Play Console > App integrity.

Without the four secrets the run still works but produces
`...-UNSIGNED-NOT-FOR-UPLOAD.aab`, which Google Play will refuse. That is only
for checking the build.

## 6. Play Console (Owner)

### Create or open the app
- Existing listing: open the app with ID `com.eswaran.beltflow`.
- New app: Create app > name "BeltFlow", default language English (United
  Kingdom) or English (United States), App, Free.

### App content (Policy > App content)

**Privacy policy:** the address from step 3.

**App access:** "All or some functionality is restricted". Give Google's
reviewers a working sign-in. Create a separate demo Persatuan with made-up
members (never real children) and a parent account in it, and enter that
e-mail and password with a short note: "Sign in, open Profile to see
Privacy and my data."

**Ads:** No, the app contains no ads.

**Content rating:** answer the questionnaire honestly. Points that apply:
users can communicate with each other (parent and instructor messages); no
violence, gambling or purchases of digital goods inside the app (class fees
and merchandise are paid to the academy).

**Target audience and content:** answer honestly. Students under 18 use the
app, so include the age groups that actually sign in. If you include
children under 13, Google's Families policy applies. BeltFlow has no ads,
no analytics and a privacy policy, which those rules require. If only
parents and staff should sign in for children under 13, say so and make sure
academies set it up that way.

**Data safety:** draft answers, matched to what the app does today:

| Question | Answer |
|---|---|
| Does the app collect or share user data? | Yes, collects |
| Is all data encrypted in transit? | Yes (HTTPS only; the production build refuses plain HTTP) |
| Can users request deletion? | Yes. In the app (Profile > Privacy and my data) and at the account-deletion web address from step 3 |
| Data shared with third parties | None. Hosting, notification delivery and payment providers process data on BeltFlow's behalf, which Google does not count as sharing. If you switch on an outside AI provider for the assistant, review this answer |

Data types collected (all for **App functionality** and **Account
management**; none for advertising or analytics; none sold):

| Type | Collected | Required or optional |
|---|---|---|
| Personal info: name | Yes | Required |
| Personal info: e-mail address | Yes | Required |
| Personal info: phone number | Yes | Required |
| Personal info: user IDs | Yes | Required |
| Personal info: other (identity card number, date of birth, if the academy records them) | Yes | Optional |
| Health and fitness: health info (medical conditions, allergies, if given) | Yes | Optional |
| Financial info: purchase history (fees, payments, receipts; no card numbers) | Yes | Required for paying members |
| Messages: other in-app messages (parent and instructor) | Yes | Optional |
| Photos and videos: videos (training videos, if uploaded) | Yes | Optional |
| App info and performance | No | |
| App activity / web browsing | No | |
| Location | No | |
| Device or other IDs (notification token) | Yes | Optional (only if notifications are allowed) |

**Government apps, financial features, health apps:** No (the app records
medical notes for training safety but is not a health app). Answer any
"financial features" question honestly: the app records fees paid to the
academy; it is not a payment service.

### Store listing (Grow > Store presence > Main store listing)

- **App name (30 max):** `BeltFlow: Martial Arts Academy`
- **Short description (80 max):**
  `Attendance, belt gradings, fees and family updates for martial arts academies.`
- **Full description:**

  > BeltFlow helps martial arts associations and academies run their classes,
  > and keeps families up to date.
  >
  > For academy administrators: set up classes and instructors, approve new
  > members, see attendance and fees across the academy.
  >
  > For instructors (Masters): take attendance, including by scanning a
  > student's QR pass, even without an internet connection; record belt
  > gradings; message parents.
  >
  > For parents: follow your own child's attendance, belt progress and fees,
  > pay through your academy's chosen method, and message the instructor.
  >
  > For students: see your syllabus, progress and certificates, and show your
  > digital pass at roll-call.
  >
  > Available in English, Bahasa Malaysia and Tamil. Your academy must use
  > BeltFlow and approve your account before you can sign in.
  >
  > Privacy: no ads, no tracking. You can download your data or ask for it to
  > be deleted from Profile > Privacy and my data.

- **Bahasa Malaysia listing** (add a translation, language Malay):
  - Short: `Kehadiran, gred tali pinggang, yuran dan info keluarga untuk akademi beladiri.`
  - Full: translate the English text above; have a native speaker check it.
- **Graphics:** app icon 512 x 512 (`mobile/assets/icon.png` rendered at
  512), feature graphic 1024 x 500, and at least two phone screenshots. Take
  screenshots from the demo academy only, never with real members' data.
- **Category:** Education (or Sports). **Contact e-mail:** your business
  e-mail.

### First upload
Test and release > Testing > Internal testing > Create release > upload the
`.aab` > release notes ("First release of BeltFlow 2.0") > Review > Start
rollout to internal testing. Add your own Google account as a tester and
install from the testing link on your phone.

## 7. Closed testing, then production (Owner)

- If your developer account is a personal account created after November
  2023, Google requires a closed test with at least 12 testers for 14 days
  before production. Play Console shows this on the Production page if it
  applies.
- Test on real phones: sign-in, attendance (online and offline), QR scan,
  parent payment flow, privacy screen. None of this has been tested on a
  physical device yet.
- Then Production > Create release > promote the tested bundle > start with
  a staged rollout (for example 20%).

`build_aab.yml`) built the earlier Kotlin app with the leaked key. It is
superseded by the Expo app in `mobile/`; do not upload its builds.
